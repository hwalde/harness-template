# 知识存放：LLM-Wiki、替代方案、规则
**核心：** 与编程智能体的协作在很大程度上就是知识管理。进入知识库的只有源代码里没有的东西；每条信息恰好属于一个上下文；谁运营一个知识库，谁就买下了维护义务。（上下文：Harness 模板 | 截至：2026-08-30）

## 向智能体供给知识的六条途径（可任意组合）
| 途径 | 描述 | 何时 |
|---|---|---|
| 1. 从 `AGENTS.md` 链接文档 | 「在本项目开始工作之前，先查看 `docs` 目录中是否有文档涉及你的主题，有则阅读。」反方向：新产出的成果存放在那里——附上什么值得存、什么不值得的指令 | 中小型项目，文档不多，团队本来就维护 Docs |
| 2. 子目录中的规则文件 | 模块专属知识随模块存放，情境化加载 | 按业务切分的目录树 + 支持此特性的智能体（[regeldateien.md](regeldateien.md)） |
| 3. rules 文件 | 绑定路径的规则（只针对 `tests/**`、只针对 `src/ui/**`） | 智能体支持 rules；规则挂在文件类型/区域上 |
| 4. Skills | 知识在被需要时才加载 | 规范目录、演进知识、操作指南（[skills-und-commands.md](skills-und-commands.md)） |
| 5. 带 librarian 的 LLM-Wiki | 结构化存储，以一个子智能体为唯一入口 | 跨越多个系统/仓库的知识、决策及其理由、运维知识、领域知识；长寿项目 |
| 6. MCP 服务器 / 脚本作为知识源 | Confluence-MCP、提供文档的脚本 | 当来源在外部时；Confluence 内容是写给人的，常常是垃圾场——智能体同样会在那里折戟 |

一切途径的前提：**模型必须得知它们的存在**——`AGENTS.md` 里的一句话。不用 RAG/Embedding 分块：靠目录树 + 索引文件的可寻性效果更好。

## 什么该进知识库——什么不该
**进：**
- **从源文件看不出来**的知识：决策及其理由（那个「为什么」）、从代码上看不出的坑、运维/访问/基础设施知识、领域和业务知识、约定、指向事实来源的指针。
- 在模型仍薄弱的领域里自己的专家知识。

**不进：**
- 源代码里本来就有的东西：「谁抄写源代码里的内容，谁就有了两份真相——而且它们会分道扬镳。」可从代码库推导的细节（清单、字段列表、Endpoint 目录、计数）会漂移、会变错 → 至多一个指针。
- 模型本来就知道的东西。
- 瞬态的运行时知识：刚刚回答过的一次性询问、进度/状态笔记、日志输出、中间状态、琐碎内容。
- Secrets——只存指向其存放位置的引用。

判断准则：**「未来的会话需要它吗？」**拿不准就不入库。模型越聪明，需要的知识文档越少；模型越小/越本地化，知识文档就越珍贵。

## 本模板中的 LLM-Wiki（Karpathy 模式）
```
.my-memory/
├── raw/    不可变的原始文件（仅追加）
└── wiki/   浓缩、相互链接的页面；每目录一个 index.md（每条一句话）；log.md
```
- 自上而下导航：永远先读 `index.md`，再有针对性地深入；交叉引用如同百科全书。两条质量规则：索引描述简洁精准（路标，不是变更日志）；不写模型本来就知道的东西。
- **librarian**（`.claude/agents/librarian.md`）是唯一的门：他取出知识（QUERY，查询）并存入知识（INGEST，入库），作为守门人过滤（馆藏知识 vs. 运行时知识），强制执行 Context Scoping，只把精华返回——主智能体不读任何 Wiki 文件，也无须琢磨什么该放哪。两条姿态规则：他从不反驳决策；他会把旧知识标注为可能已过时。
- `AGENTS.md` 中的规则（紧凑、有理由）：工作开始时先问它，再问用户；结束时把留得下来的东西入库；绝不直接读写 `.my-memory/`。若智能体无视 librarian，就让模型自己重新拟这条规则——紧凑、有理由、不与系统提示词对着干。
- **Context Scoping：** 每条信息属于一个上下文（项目、子系统、目标群体、客户、工具）——以目录子树呈现；否则智能体会把不相干的东西联系起来。
- **策展**（持续义务）：知识会过时，然后反过来害人。周期性地、经明确触发地进行（MAINTENANCE 模式，即维护；大型 Wiki 可建专门的策展 Skill）：合并冗余、把漂移的细节转为指针、标记过时内容、理顺索引描述、清除死链。绝不顺手做，删除绝不缺批准。
- 实践中的结论：跨项目（多个仓库/系统的联合体）非常成熟可靠；对单个、高度以代码为中心的项目，一个 `docs` 目录可能就够了。

## 设置时的决策辅助
| 问题 | 是 → | 否 → |
|---|---|---|
| 是否存在不在任何仓库中的知识（运维、访问、领域、决策），且项目存续超过几周？ | 带 librarian 的 LLM-Wiki | `docs` 目录 + 从 `AGENTS.md` 链接 |
| 目录树是否按业务切分、且智能体加载子目录规则文件？ | 模块专属知识进子目录 `AGENTS.md` | 进 `docs/` 或 Wiki |
| 规则是否挂在文件类型/区域上、且智能体支持 rules？ | rules 文件 | 子目录规则文件或 `AGENTS.md` 段落 |
| 是否有大型规范/指南目录？ | Skill | `AGENTS.md` 中的简短段落 |

若 Wiki 不被使用：删除 `.my-memory/`、librarian 以及 `AGENTS.md` 中的 Wiki 规则（半吊子的安装对智能体的困扰大于帮助）。
