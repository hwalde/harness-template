# 评估者：生成者 → 评估者
**核心：** 干活的那个智能体被问「干得好吗？」时永远答是。第二个智能体——上下文全新、无写权限、对照被观察到的证据——会发现不同的问题。该模式 = 一个子智能体 + 规则文件里的一个条目。（上下文：Harness 模板 | 截至：2026-08-30）

## 模式本身
| 部分 | 内容 |
|---|---|
| 子智能体 `evaluator`（`.claude/agents/evaluator.md`） | 怀疑型第二审查者；怀疑态度明写在提示词里；阅读规格、`git status`/`git diff`（必要时还有提交历史），打开每份证据，尽可能亲自观察（测试、构建、冒烟检查）；无 Write/Edit 权限；以 `PASS` 或 `NEEDS_WORK` + 具体 Findings 回复 |
| `AGENTS.md` 中的验收义务 | 「在任何东西被称为『完成』或『能用』之前，由 evaluator 以全新上下文、无写权限、对照被观察到的证据进行检验。`NEEDS_WORK` → 处理 Findings → 再次送检，直到 `PASS`。」没有这个条目，子智能体不会被使用。 |
| 循环 | 构建 → 评估者 → 修复 → 评估者……直到 `PASS`。不辩论、不搪塞、不弱化测试。 |

实践中的效果：错误率明显更低；评估者经常发现尚未搞定的东西。代价：几个 Token 和一点时间。

## 调用方要提供什么
评估者不相信任何断言——所以要产生可核验的证据并加以引用：
1. 任务 / 验收标准（规格、工单、计划、检查清单）。
2. 改动范围（文件；有 Git 时他自己获取 Diff）。
3. 证据：测试日志、构建输出、截图、渲染产物——以路径给出。
4. 可选一个侧重点（见下）。

给评估者的提示词写成信，不写成命令清单：他是同一个模型、具备完整的认知能力；给他思考的空间，不要越俎代庖。

## 局限与对策
- 模型越叛逆，越容易绕开评估者或试图欺骗他（模型确实会欺骗）：只给评估者递一个局部侧面、弱化测试、「已知限制」。评估者提示词里的对策：范围检查、Builder 的借口不算数、被弱化的测试是一条独立 Finding。
- 谁来启动评估者：(a) 实施工作的智能体自己——最简单的一级，本模板即如此；(b) 从外部经 Hook（如 Stop-Hook 或 Pre-Commit）——智能体再也无法忘掉他；(c) 在 CI/CD 流水线中，Findings 进评审平台——「再好一点」，因为独立。设置时决定是否额外要 (b) 或 (c)。
- 一个绿色的测试只证明该测试走过的那条路径。成文的检验标准才是尺度；没有标准时评估者对照任务描述检验，并把这一点说明。

## 多个与专项评估者
最小的建制是一个评估者。更大规模：多个实例依次运行（Anthropic 内部会跑一整排），按项目情况分主题侧重。两条路：

1. **一个评估者，多个侧重点**（模板内建）：多次调用 `evaluator`，分别带「侧重点：安全」/「性能」/「Clean Code」/「编码规范」/「架构」。没有额外的常驻上下文，因为只加载了一份描述。
2. **每个侧重点一个自建子智能体**（可在设置时创建，见下方模板）：当某个侧重点需要专属知识（架构文档、规范目录、一份安全检查清单），或要在流水线/CI 中单独运行时，才有意义。

多个评估者运行时的顺序：先确定性检查（Linter、静态分析、测试——用脚本，不用模型），再功能验收（标准评估者），然后各侧重点（安全 → 架构/规范 → 性能 → Clean Code）。每个评估者都经 `git status`/`git diff` 查看改动，并向主智能体返回具体、可修复的 Findings；主智能体逐项处理后再次送检。不必事事全上：在 `AGENTS.md` 中确定哪些评估者在何种改动规模下运行（例如安全在涉及认证/输入/文件访问时一律运行；架构在新模块时）。

## 专项评估者的模板
文件 `.claude/agents/evaluator-<侧重点>.md`（用 `tools/sync-agents.py` 转换给其他智能体）：

```markdown
---
name: evaluator-sicherheit
description: >-
  安全审查者（生成者→评估者）。在认证、授权、输入处理、文件/网络访问或依赖项发生
  改动后、工作被视为完成之前调用。以全新上下文阅读 Diff 和证据，对照 AGENTS.md/docs
  中的安全规则检验，以 PASS 或 NEEDS_WORK 回复。无写权限。
tools: Read, Glob, Grep, Bash
model: opus
---

你只从安全的角度检验另一个智能体的改动。你不相信任何断言；你负责评判，不负责修复。

1. 查看 `git status` 和 `git diff`；完整阅读涉及的文件。
2. 检验：输入校验、注入（SQL/Shell/Prompt）、AuthN/AuthZ、代码/日志/提交中的 Secrets、
   不安全的默认值、超出允许范围的路径、新增依赖、泄露内部实现的错误处理。
   项目专属规则：<文档路径>。
3. 尽可能亲自观察（经 Bash 运行测试、Linter、安全扫描器）。

回复：第一行 `PASS` 或 `NEEDS_WORK`。之后每条 Finding：文件:行号、风险、
期望行为、具体修复建议。阻塞性 Findings 排前。不要总结 Diff。
```

类推：`evaluator-performance`（复杂度、N+1、热路径中的 IO、内存、缓存/批处理）、`evaluator-clean-code`（可读性、命名、重复、函数体量、死路径）、`evaluator-guidelines`（读取规范 Skill/文档并逐条检验）、`evaluator-architektur`（读取架构文档，检验层边界、依赖方向、模块划分）。每个侧重点评估者都在 `AGENTS.md` 中获得一句「何时运行」。

## 其他行之有效的子智能体类型（供参考）
| 类型 | 任务 |
|---|---|
| librarian | 知识库的唯一入口 → [wissensablage.md](wissensablage.md) |
| 文档维护者 | 每次提交前跟进文档；检验标准写在提示词里 |
| 远程系统专家 | 凭已入库的知识回答关于生产环境的问题；不带工具 |
| 链接模式 | 代替 Custom Subagent：提示词放在一个文件里 + `AGENTS.md` 中三行话「启动一个读取该文件的子智能体」——无常驻上下文 |

Custom Subagent = 带 Frontmatter（`name`、`description`、`tools`、`model`，可选 `color`）的 Markdown 加提示词；`description` 决定主智能体是否会用它；`tools` 保持最小；描述在每次请求时消耗上下文——只建经常被需要的。
