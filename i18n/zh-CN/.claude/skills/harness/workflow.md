# 工作流：从委托到通过验收的工作
**核心：** `AGENTS.md` 中的标准工作流确定顺序：获取前置知识 → 规划（够用即可）→ 带确定性检查地实现 → 评估者循环 → 跟进文档和 Wiki。过度规划的对极是一个精炼的目标加检验标准。（上下文：Harness 模板 | 截至：2026-08-30）

## 标准工作流（`AGENTS.md` 的建议稿，设置时裁剪）
1. **前置知识：** librarian QUERY（查询）并带上意图；阅读涉及该主题的链接文档（子目录规则文件由智能体情境化加载）。
2. **规划，够用即可**（层级见下）。把验收标准写成可勾选的形式——它们是评估者的尺度。
3. **实现。** 确定性的交给脚本：格式化、Linter、静态分析、测试、构建。Web/桌面应用中途自己看一眼（浏览器/桌面操控），最后跑可重复的测试。
4. **验收：** evaluator，带上标准、Diff 和证据；`NEEDS_WORK` 就返工并再次送检，直到 `PASS`。侧重点评估者按改动规模（[evaluatoren.md](evaluatoren.md)）。
5. **跟进：** 更新文档/规格；留得下来的经 librarian 入库（只存未来会话需要的）；某句话被重复需要时在 `AGENTS.md` 加一句；发布/部署只经指定的脚本。

这是顺序，不是表格：一行的修复不需要计划，但每个改动都需要验收。

## 一个任务需要多少规划
| 层级 | 何时 | 做法 |
|---|---|---|
| 1 – 放手去做 | 不复杂（改按钮颜色、小修复） | 直接从聊天里实现；如今覆盖大多数情况 |
| 1+ – 让它规划 | 想要多一点结构 | 智能体的规划模式 → 技术方案 → 实现 |
| 2 – 计划进文件 | 层级 1 撑不住；想要全新的上下文 | 让它把计划写进文件，然后**2–4 轮修正**（「再过一遍对话记录，实现还缺什么吗？」）——第一次追问总能补出实质内容；在新聊天里只凭该计划实现 |
| 3 – 需求文档 | 真正的大活；技术方案会变成累赘（约 800 行尚好，4000 行糟糕） | 带编号的业务需求（写什么，不写在哪个文件）+ 实现工作包（每条需求至少归入一个包——修正轮）+ **每包的测试要求** + Harness 薄弱时附测试信息（可用工具、API 文档、MCP 服务器）。每包两条附加要求：实现后重读文档并勾选；为后续包补写简短的实现提示。每包一个聊天或子智能体 |

由此形成循环**读文档 → 工作 → 更新文档**：需求或计划文档持续被续写，是下一个聊天或子智能体的知识来源。

**对极（可行之处优先）：** 目标 + 检验标准，代替流程计划。「流水线成本要低于 10 美元；通过 X 处的费用查询验证。」提示词工作并没有消失，它从做法挪进了目标和标准（[autonome-laeufe.md](autonome-laeufe.md)）。逐项询问需求的框架（Spec-Kit 之类）是辅助轮——在不熟练时有用。

**前置工作流：** 工单 + Braindump（一切智能体无从得知的：会议、方向、顾虑、自己的问题）→ 3–8 个子智能体并行做信息采集（「X 我们是怎么建的，需要重构吗？」）→ 让智能体给出解决路线，人来拍板。此时聊天是「一座藏着珍珠的垃圾场」；从层级 2 起只把珍珠传下去。

## 工作流中的测试
- 测试金字塔依旧成立。有了 AI，测试比以前更有价值，因为智能体用它验证自己的结果；E2E 测试放最后，不妨一开始就写好；解析器类任务预先给出输入/输出对（「用它们给自己搭 Unit-Tests」）。
- 不要给一份手工测试脚本让它照着走——让它据此生成可重复的 E2E 测试（点一遍的质量看当天状态）。
- 浏览器/桌面操控是中途看一眼用的，不是测试用的；确定性的状态检查（服务器在跑？端口？Health？日志？）是脚本的事。
- 为智能体整理测试结果（脚本：失败的测试逐个重跑，每个测试对应浏览器日志/网络/服务器日志、条目年龄）——智能体没有时间感。
- 改造之后：「把测试理顺；发现 Bug 不要掩盖，写下来。」
- 凡涉及人类视觉判断之处（界面的合理性、专用软件、视频），人工终验保留。把它放到最后，别让智能体一路上每个 Edge Case 都截图送检。

## 表述委托（简版）
- 晶莹剔透、就事论事；把**为什么**和质量层次一并给出（演示用的原型 vs. 生产系统）。
- 上下文：写进去、让它去取（并说在哪）、或——有 Harness——让它自己取。
- 示例对顶级模型要省着用（源代码就是示例：「照 User-Service 那样」）；对小模型要给足。
- 只有背后有自己的观察时才规定做法；否则点出能力（「使用子智能体」），用法交给它。
- 面对意外的行为准则：边界与中止条件（[autonome-laeufe.md](autonome-laeufe.md)）。
- 工具指名道姓（要求或禁止）；对外动作设限（「填写，不要提交」）。
- 外来文本用 XML 标签框起来；「排版，不要改写」；「一字不差写进一个文件」。
- 给其他实例/子智能体的委托写成**信**，不写成命令清单：「记住那个实例和你是同一个模型，会完整地投入思考——给它留思考的空间。」
- 三个控制性提问：「用你的话复述我说了什么。」·「还有没有开放的、**相关的**问题？」· 过度规划之后：「有没有矛盾？」
- 数量用数字不用形容词；文本量用脚本来量。

## 追问政策
设置时确定：交互式（允许追问，最好打包提出并使用智能体的提问工具）或全自主（除非被要求否则不追问；作出最佳的、有依据的假设，记录下来，继续干；提问轮只在启动前）。无人值守的运行一律适用后者。

## Dynamic Workflows 与评估者链
- 常规：主智能体启动子智能体 → 读报告 → 思考 → 下一个。**Dynamic Workflow**（Claude Code：Workflow 脚本）省掉中间环节：主智能体写一个由子智能体调用组成的脚本（各带模型、类型、提示词、输出模式），执行它，最后拿到一份报告；结果以文本流入下一个提示词。优点：步骤之间不用思考；缺点：恰恰缺了思考。只在用户明确同意时使用——很多智能体、很多 Token。
- 多个评估者的接力可以这样编成链（前一个的 Findings 进下一个的提示词），或者干脆由主智能体顺序调用。
- 主智能体当管理者：长运行中它只做编排；子智能体负责实现。带角色和沟通规则的集群（Swarms）未被证明有效。

## Harness 在日常中顺带生长
每个被敲第二遍的句子变成一条规则；每件算法化的手工活变成一个脚本；每项重复出现的检验变成一个评估者；每个成功的流程变成一个 Skill（「有没有值得作为 Skill 复用的部分？」）。
